# 卡片删除回归报告

日期为 2026-11-24。修复前版本为 `d2eb37e`，修复版本为 `d8501a0`。测试使用本地 React 前端、FastAPI 后端和 `127.0.0.1:5433/livingatlas_test` 上的 PostgreSQL 17。附件通过本地磁盘替代 Azure Blob Storage。所有写入使用合成账号和卡片。

| 检查 | 修复前 | 修复后 |
|---|---|---|
| 管理员用原有用户名和标题删除普通卡片 | HTTP 500，`relation "favorites" does not exist` | 启动迁移（startup migration）创建遗漏的收藏表，原请求返回 HTTP 200 |
| 管理员改标题后未保存，直接点击删除 | 组件测试（component test）捕获到请求发送草稿标题 | 请求使用卡片编号和已保存的用户名、标题。元数据（metadata）已提交但图片排序保存失败时，也使用已提交的标题 |
| 同一账号的两张同名卡片 | 旧查询可命中任一张 | 带编号的请求只删除目标。旧请求遇到歧义时返回 HTTP 409 |
| 两个同时提交的删除请求 | 未测 | 一个成功，一个返回 HTTP 404。同名的第二张卡片仍在 |
| 普通账号、空请求者邮箱、已改名的旧卡片 | 未测 | 分别返回 HTTP 403、403 和 404。卡片和附件保留 |
| 图片、附件和收藏 | 只读取第一条附件记录，部分文件在事务（transaction）提交前删除 | 提交后清理全部无引用的测试文件和图片，清理收藏记录。其他卡片引用的文件保留。两次同名新上传使用不同存储路径 |

从后端目录运行 `python -m scripts.check_card_deletion --baseline` 可验证原请求。运行 `python -m scripts.check_card_deletion` 可检查数据库行数、本地文件和数据清理。相邻的联系人权限测试 `python -m scripts.check_card_contact_email` 通过。附件、存储和图库共 30 项后端测试通过。前端图库、关闭卡片、位置编辑和更新记录共 67 项测试通过。

Edge 浏览器测试使用合成管理员的本地登录状态。打开另一账号的卡片，修改标题后直接确认删除，界面显示 `Project deleted successfully.`，后端返回 HTTP 200。浏览器快照和后端日志保存在本机忽略目录 `backend/.local-postgres/`。

本地结果确认了缺表和草稿标题两条失败路径。线上反馈发生于 11 月 20 日，实际删除时间和请求响应未知。管理后台（Admin Dashboard）的 `Last Online` 只在验证登录凭据时尝试写入。恢复浏览器中已有的登录状态和删除项目都不会更新时间，因此 10 月 27 日的记录无法确定故障日期。线上日志和 Azure 文件删除未在本轮验证。

删除接口依然使用客户端提供的邮箱查询角色，缺少服务端验证的会话凭证（session credential）。本轮验证了数据库角色和卡片所有权的比较，未覆盖完整的身份验证（authentication）流程。
